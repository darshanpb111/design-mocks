1Object linking — the schema and how a layer finds its style

Exactly one new field — the template lookup — on each of the two existing objects (corrected 12 Aug, Darshan): a Map_Layer__c is one asset type on Sitetracker — one MOC lookup, one Layer_Type__c — hence one geometry, so per-geometry lookup triplets were over-modelling. The one anomaly is a mixed-geometry file upload (points+lines in one KML, FileLayerHandler.js:300 renders children off one record): the applied template styles the children matching its geometry, remaining geometries use the org default — noted below.

Apply = live reference to immutable published versions. Shared edit prompts "apply to all N / copy for this layer" — copy-on-write, never silent, never a merge.

2Data storage — what lives where, and what it costs

Two Salesforce pools: data storage (records) and file storage (ContentVersion files). The design splits deliberately across them.

WhatStored inPoolCost
Template graph (template + rules + stops + assets)custom-object recordsData ~2 KB per record, flat — long-text content does not add. Worst-case template ≈ 607 records ≈ 1.2 MB; 100 templates ≈ 0.1 GB
Compiled style documentdropped 12 Aug — clients render from the record itself (scalar fields + value JSON)— ≤ 50 KB target, still counts ~2 KB — effectively free
Icon renditions (data-URI PNGs)on each asset record (st_Png_Renditions__c) — fetched per asset, cachedData ≤ 200 KB per template cap
Uploaded SVG/PNG originalsContentVersion (uploaded over REST — never Apex heap)File caps: 5 MB/file, 50 per type → absolute worst 500 MB; realistic ~20 MB
Org capacity (Enterprise/Unlimited)Data: 10 GB + ~20 MB/user · File: 10 GB + ~2 GB/user ample a 50-user org has ~110 GB file storage
The binding constraint is not org storage — it's the 131,072-character cap on a single long-text field. First Phase-1 task: compile a worst-case template (100 values + 20 icons) and measure. Outcome decides: one field, or manifest split to its own field/ContentVersion. Everything else in the storage design is settled.

(blocks delete, feeds the tooltip)

Which template is active for this layer? 
// per geometry — first non-null wins:
layer.st_Style_Template__c                 // 1. layer link
?? layer.Map_Object_Configuration__r
        .st_Style_Template__c               // 2. object-config link
?? orgDefaultId                             // 3. cached in GIS config CMT

Two meanings kept distinct: the resolved template above (what the map paints, what the switcher pins to top) vs the org-wide st_Status__c='Active' lifecycle state. Status is checked at link time only — an Archived template keeps resolving for layers that already reference it, so archiving never restyles a field user's map.
Is this template editable by me? 
editable =
     t.st_Provided_By__c == 'Organization'       // ONE rule: shipped + imported templates are read-only; clone stamps Organization
  && t.st_Status__c != 'Archived'           // unarchive first
  && FeatureManagement.checkPermission('st_GISLink_ManageStyleTemplate')
  && [SELECT HasEditAccess FROM UserRecordAccess
      WHERE UserId=:uid AND RecordId=:t.Id].HasEditAccess  // __Share rows
Five independent predicates — the two locks are deliberately separate fields, the last one is the record-access model: UserRecordAccess.HasEditAccess natively reflects OWD + our __Share rows, so the UI never re-implements sharing math. Not editable ≠ hidden: read-only opens the panel with controls disabled and "Save as new" as the escape hatch.

3Format — the record IS the contract

Admins author the record; clients read the same record — scalar fields + the per-value JSON — and build renderers client-side (dropped compiled doc, 12 Aug). Below, the legacy framing: compiled document — validated, inheritance-resolved, Esri-renderer semantics (so ArcGIS imports map near-losslessly and mobile's existing types already match).

Inheritance — resolved once, at publish
Rule.Simple symboldeep-merge, per-property → Stop sparse override→ × layer opacity→ resolved symbol in the doc

Categorical derives from Simple until a value is overridden (final). A 40-value classification with 3 custom values stores 3 sparse stops. Clients (web and mobile) carry zero inheritance logic. As-Built falls back to Design when absent. Per-layer deviation = clone (copy-on-write), never stored overrides.

Cross-SDK rendering limitations — design-facing, every surface

The template renders on two engines: web = ArcGIS JS 4.34 (Lightning Maps beta, Site Central and every embed — one consumer) and mobile = Mapbox v11 via rnmapbox 10.3.1 (parked v1, but the contract must survive it). Legacy V1 web maps and the old mobile Map screen never render templates — no limitation surface there. Per the PRD's own rule these inform, never gate — but design should know where the SAME template will look different per platform.

Packaging — can we add new objects, and where do they go?

Yes — new custom objects and new fields on existing packaged objects are additive changes, supported in upgrades for both 1GP and 2GP. The 1GP caveat that matters: once released, packaged components can never be deleted or renamed — API names are permanent. (One more reason the naming decisions — the template-association question T1, the two lock fields — are settled before Phase 1 ships.)

R2Why 2 objects — and why not 1, 3, 4, or something existing

The schema was challenged twice and got better both times. The reasoning, so a reviewer doesn't have to re-litigate it:

Why not ONE object with everything in JSON? Two things can't live inside a blob: (1) icons are shared — one uploaded image is used by many templates, carries its own file (ContentVersion), caps and dedup, so it must be its own record; (2) "can't delete an icon in use" needs a real foreign key — with icon references as strings inside JSON, the check is an unindexable text-scan and nothing stops a direct API delete. The single-valued Simple icon gets a real Restrict lookup; per-value references are enforced by a before-delete trigger at the same database boundary.

Why not FOUR (the original design: Template → Rule → Stop records)? Challenged 11 Aug ("why child records when the template is JSON anyway?") and it didn't survive: validation is compiler work either way, locking is whole-template, sharing is template-level, and the record graph had to be serialized to JSON for checksums regardless — so the records were a normalized copy of a JSON that existed anyway, at the cost of reconciling up to ~600 child rows on every Save vs one update. The prototype's own save model (one snapshot string) is the blob shape.

Why not an EXISTING object? Nine candidates were evaluated (doc 16 §1b). The recurring disqualifiers: Layer_Styling__c is a per-layer field, not shareable/versionable; GIS_Sync_Template__c models field mappings, not renderers; Custom Metadata Types (the PT-status-colours pattern) need an async metadata deploy per admin save, have no record sharing, and can't be the target of a Restrict lookup — that authoring experience is exactly what this feature escapes. One CMT survives as the kill-switch only.

So: 2. Map_Style_Template__c (the unit users name, share, and apply) · Map_Style_Asset__c (the unit that outlives any one template). A usage junction briefly connected them (11 Aug) until the same test that killed the other bookkeeping killed it too: its rows were code-maintained at every save. Delete-protection now = the template's st_Icon_Asset__c Restrict lookup (Simple icon) + a before-delete scan of template JSON (per-value icons).

R4When things happen — the workflows, end to end

FlowWhat happens, in order
Create a templateNew record (Draft) → user edits in the builder → Save = the whole lifecycle (publish collapsed into save, 12 Aug): the service validates (USER_MODE) and writes the scalar fields + st_Value_Styles__c; first save to Active makes it pickable
Apply / switch on a layerSets the layer's st_Style_Template__c lookup — the template (incl. its Simple/Categorical mode) fully describes the look. Map re-renders from the published doc. Switching back to ST Default is the only "removal" — there is no detach
Import an ArcGIS layerLayer syncs → its renderer is forked into a new template (st_Provided_By__c=ArcGIS) → auto-applied to the layer → icons/colours land in the org asset library → user edits freely; nothing ever writes back to ArcGIS; the UI says so
Upload a shapefile / GeoJSONNo styling exists in the file → layer gets the org default template (ST Default: 3 colours — sites / segments / areas) → user switches or creates a template from there. KML additionally parses its embedded styles into a seeded template (notice shown only if parsing fails)
Edit a template others usePublish updates the shared doc. Other sessions viewing affected layers get "this template was updated while you were away — load the latest / keep viewing yours" — never a silent restyle. The same message covers "someone published while you were editing"
Delete an iconThe platform refuses if any template's st_Icon_Asset__c points at it (Restrict); the before-delete trigger scans per-value references and blocks with "in use by: X, Y"
Delete / archive a templateBlocked while any layer links it: row-level delete AND archive controls disabled (bulk bar + right-click), "in use" badge explains why. Hard delete only at zero references
Re-sync an ArcGIS layerThe only moment source-styling changes can surface (no auto-detection exists) → the layer's own st_Style_Template__c IS the fork (no source-id field needed) → sync flow offers "sync styles too": update it from source, or keep it
