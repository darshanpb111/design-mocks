The arithmetic, stated plainly

The team's own band delivered 14 of its 17 items (82%) this sprint. At that rate, two remaining sprints absorb roughly 28 items against 43 open — a gap of about 15. That gap closes only if the team's allocation shifts back toward its own band, or if the unscheduled tail was never really PI-11 scope.

That second reading is the more likely one, and it is the scope question worth asking: 21 PI-tagged items sit in no sprint and 33 carry no release, with two sprints left. If they belong to PI-12, the PI-11 number is honest and the tag is wrong. If they belong to PI-11, the increment is over-committed by roughly a third. The board cannot tell you which, and the difference is the whole answer.

Risks and asks

Ranked by consequence. Each says where it should actually be decided — most of these belong to planning on Monday or Tuesday, not to this hour.

R1 A new error appeared with 102.0.0 and is now the largest single error source in the field Unassigned

A type error on the record detail screen was first seen on 7 August and has produced 52,581 events across 775 users. It appears only on 102.0.0 builds — zero occurrences on 101.2.0 or any earlier release — so it arrived with this release rather than being inherited. It is an unhandled promise rejection, which means it degrades whatever the screen was loading rather than crashing the app, but it accounts for roughly a third of all error volume on the release. Sentry still lists it as unresolved and new.

The affected screen is the generic mobile record view, not one of this band’s surfaces — so this is very unlikely to be our code. That is not a reason to drop it from the review: it ships in the release carrying our work, and it is the reason the ask below is name an owner rather than assign it to us.

Two things make it harder than it needs to be: the stack arrives unsymbolicated, so nobody can see which module it is, and it is going unnoticed because error-rate-per-release is not something anyone currently watches.

Learnings — what the sprint's own data shows

  • Patch eligibility is being discovered at release time instead of at authoring time. The preferred-basemap feature was reverted out of the patch release, and patch-ineligible labels had to be stripped from the patch branch — two separate incidents, same root cause. The working rule already exists (keep patch-safe bundled code in a separate PR from Apex and metadata that a patch cannot carry); this sprint is the evidence for applying it when the PR is structured rather than when the release is cut.
  • Crash triage is slower than it should be because symbolication was missing. The largest error on the new release arrives as raw bundle offsets with no module name. The fix — publishing source maps and debug ids with the over-the-air bundles — merged on 13 August, five days after the release it would have helped.
  • Test discipline held. Every merged change checked reported clean typecheck and lint, and coverage on touched files stayed above gate, including a change that lifted branch coverage on an existing module from 76% to 84%.

These are the data-backed learnings. The retrospective's own learnings are the team's to add.

Today that claim rests entirely on local and review-time verification. Going into a 7 September release and a reference-ability conversation with no field performance evidence is the weakest part of the current position — and unlike most items on this page, it cannot be fixed retroactively. More detail — how these numbers were derived
  • Sprint identified by count match, not guessed: an open-sprints query scoped to the band and a direct query on sprint 725 both returned 17, proving 725 is the only open Eagles sprint.
  • The band field holds multiple values, and support work for another band is filed under that band. The 53-item figure comes from querying each roster member with no band filter and taking the union; the 17-item figure is the band-scoped view alone.
  • Carry-in is derived from status history — items already in progress, review, QA or verification on Monday 3 August. Sprint tags cannot answer this, because moved items do not reliably retain the previous sprint id.
  • Scope changes are not derivable. Jira exposes no historical operator on sprint membership. This is the entire reason the planning-Tuesday snapshot exists, and why its absence (R5) is reported rather than papered over.
  • "Done" means Released, Ready for Release, or Closed. One of the nine closures was closed as expected behaviour rather than delivered, and is counted separately — a valid investigation outcome, not a delivery.
  • Points are the "Beers" field. 25 of 53 items are pointed, so points and counts are both reported and neither is complete on its own.
